Kiến trúc DB: Postgres primary/standby → CockroachDB 3‑node

So sánh trực tiếp kiến trúc cluster K3s cũ (đang chạy production) và mới (đã chốt thiết kế, code T1 xong, chờ Phase 0) — trọng tâm là sự thay đổi ở tầng database: điều gì đạt được, điều gì phải đánh đổi.

00 · TỔNG QUAN

Topology thay đổi thế nào

Cũ: 1 primary ghi + 1 standby đọc-thay-thế bị động, nối bằng streaming replication một chiều. Mới: 3 node ngang hàng, đồng thuận qua Raft — không còn khái niệm "primary".

Kéo từng khối để so sánh — lưu ý: cũ có 1 mũi tên nét đứt bất đối xứng (standby thụ động), mới có vòng liên kết đối xứng cả 3 node.

Cũ — vai trò cố định

  • 1 Postgres primary (StatefulSet, hostPath /var/lib/k8s-pgdata, ghim node rhein‑13700hxes)
  • 1 Postgres standby (ghim node rhein‑k8s‑s2), streaming replication qua pg_basebackup
  • db-adapter = PgBouncer, pool_mode transaction, chỉ trỏ 1 host

Mới — vai trò ngang hàng

  • 3 node CockroachDB bare metal (systemd, không phải K8s pod) nối qua Tailscale mesh
  • Không còn "primary/standby" — mọi node đều nhận đọc/ghi, dữ liệu replicate 3 lần (RF=3)
  • db-adapter = HAProxy round-robin cả 3 node
01 · FAILURE HANDLING

Một node chết thì chuyện gì xảy ra?

Đây là điểm khác biệt lớn nhất — và cũng là lý do chính khiến việc migrate được đề xuất.

Cùng một sự cố "1 node chết" — thời gian phục hồi khác nhau theo cấp số: phút/giờ (cần người) vs giây (tự động).

03 · LỢI THẾ ĐẠT ĐƯỢC

Đổi kiến trúc để được gì

Hết master-slave

  • Xoá đúng mô hình user từng tuyên bố "tệ nhất" (ADR 200626)
  • Không còn khái niệm node "quan trọng hơn" node khác

Failover thật, không cần tay

  • Mất 1/3 node: tự phục hồi trong vài giây
  • Không phụ thuộc việc có người trực lúc sự cố xảy ra

Mọi node đều ghi được

  • Standby cũ chỉ đọc, bị động — nay 3 node đều nhận write
  • Tận dụng tài nguyên đều hơn, không có node "rảnh rỗi"

Consistency mạnh hơn

  • SERIALIZABLE thay vì READ COMMITTED — loại trừ nhiều lớp anomaly
  • Khớp đúng triết lý "DB bare metal" đã ghi trong ADR trước đó

Nền tảng để scale sau này

  • Thêm node thứ 4, 5... không cần thiết kế lại từ đầu
  • Media multi-node (nhạc YouTube ở node khác) có chỗ đứng tự nhiên

Sản phẩm phụ hữu ích

  • Audit trước khi implement đã bắt được 2 chỗ git/live lệch nhau thật
  • Lộ ra nguyên nhân sâu của DNS flakiness (CoreDNS 1 replica + search-domain)
04 · CÁI GIÁ PHẢI TRẢ

Không có gì miễn phí

Vận hành phức tạp hơn

  • 3 systemd unit tự quản thay vì 1 StatefulSet + 1 standby do K8s lo
  • Upgrade CRDB phải làm từng host, theo dõi rolling
  • Cần thêm scrape target Prometheus cho từng node

Code nặng hơn

  • WithRetry/Transact phải bọc mọi write path — đã làm ở T1, nhưng là chi phí thật đã trả
  • Sai sót ở 1 chỗ (side-effect trong closure retry) → bug âm thầm khó tái hiện

Tài nguyên nặng hơn

  • CockroachDB tốn RAM/CPU hơn postgres:16-alpine đáng kể mỗi node
  • 3 node CRDB > 1 primary + 1 standby Postgres về tổng tài nguyên

Độ nhạy mới: đồng hồ hệ thống

  • CRDB tự kill node khi lệch giờ >500ms — WSL2 vốn nổi tiếng trôi clock
  • Bắt buộc time-sync (ntp/systemd-timesyncd) trên cả 3 host, việc Postgres cũ không cần
