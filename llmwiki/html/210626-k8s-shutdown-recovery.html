Tắt máy để update
— chuyện gì xảy ra?

Phân tích đầy đủ K3S cluster Cozyroom: khi bạn tắt máy chính (rhein-13700hxes) để update Windows/BIOS, dịch vụ nào ngưng, dịch vụ nào tự sống sót, và sau khi bật lại cần làm gì. Kết luận nhanh: khá an toàn — postgres không bị auto-promote, data giữ nguyên, frontend vẫn accessible.

01 · Topology

Cluster layout hiện tại

3 nodes — 1 primary (máy chính Windows 11), 1 standby (server riêng), 1 excluded (broken networking).

K3S Master node

  • K3S control plane chạy trong WSL2 Ubuntu-22.04 trên máy Windows chính
  • rhein-k8s-s2 là worker/agent node — không có API server
  • Khi primary tắt: API server down → không schedule pod mới, nhưng kubelet trên worker vẫn chạy pod hiện tại

Private Registry

  • Docker container tại Tailscale IP 100.88.197.64:5000
  • Chạy trên máy chính → khi tắt máy, registry down
  • Pod đang chạy KHÔNG bị ảnh hưởng (image đã cached)
  • Chỉ ảnh hưởng nếu pod cần pull image mới sau restart
02 · Khi tắt máy

Timeline từ tắt đến khởi động lại

Chuỗi sự kiện khi bạn shutdown máy chính. Mỗi bước xảy ra theo thứ tự này.

Điểm an toàn then chốt: postgres-monitor CronJob có nodeSelector: rhein-13700hxes — nó chỉ schedule được trên primary node. Khi primary tắt, CronJob bị kẹt ở trạng thái Pending và không thể chạy → standby không bị auto-promote. Postgres data hoàn toàn an toàn trong suốt quá trình reboot.

WSL2 auto-start — ✓ Đã xác nhận

  • systemctl is-enabled k3s → enabled
  • systemctl is-active k3s → active
  • K3S systemd service tự start khi WSL2 boot — không cần can thiệp.

Registry auto-start — ✓ Đã xác nhận

  • k3s-registry: RestartPolicy=always
  • Container tự restart khi Docker daemon khởi động lại.
  • Pod đang chạy không cần re-pull → ổn dù registry chậm start
03 · Sống sót / Ngưng

Từng dịch vụ — trạng thái khi primary offline

Bảng đầy đủ: replica count, node pinning, và kết quả khi primary (rhein-13700hxes) đang tắt.

postgres (primary) 1 Required: primary node NGƯNG Mọi write/read từ app đều fail
backend 1 Required: primary node NGƯNG Toàn bộ API: 502 / connection refused
postgres-standby 1 Required: standby node CHẠY Hot standby read-only — không promote tự động
frontend 3 (anti-affinity) Exclude: e2144g; spread across nodes 2/3 còn sống UI load được; API calls fail (backend down)
cloudflared 2 (anti-affinity) Exclude: e2144g; spread across nodes 1/2 còn sống music.giatbh.io.vn vẫn accessible

User experience trong thời gian tắt

  • Trang web load được (frontend + cloudflared sống trên standby)
  • Danh sách nhạc, video, sách không hiển thị (API down)
  • AI chat không hoạt động (backend down)
  • Playback nhạc hiện tại (nếu đang chơi trên client) vẫn tiếp tục — player là client-side

Postgres replication sau restart

  • Khi primary down: standby vào trạng thái recovery paused, vẫn readable, không nhận WAL mới
  • Khi primary restart: streaming replication tự resume — standby tự reconnect, sync lại WAL gap
  • Không cần pg_basebackup lại trừ khi gap WAL quá lớn (mặc định giữ 256MB)
04 · Trước khi tắt

Checklist trước khi shutdown

Những việc nên làm để đảm bảo tắt máy sạch sẽ. Đánh dấu từng mục trước khi nhấn Shutdown.

Kiểm tra dữ liệu đang xử lý

Ghi chú trạng thái

Nếu muốn zero-downtime cho người dùng khác: Trước khi tắt, scale frontend lên node standby: kubectl scale deployment/backend -n cozyroom-k8s --replicas=0 để tránh connection timeout storm khi backend mất đột ngột. Scale lại sau restart.

Lệnh nhanh kiểm tra trước shutdown

wsl -d Ubuntu-22.04 -- bash -c "
# Tình trạng cluster
kubectl get nodes -n cozyroom-k8s
kubectl get pods -n cozyroom-k8s

# Replication status
kubectl exec -n cozyroom-k8s statefulset/postgres -- \
  psql -U cozyroom -c 'SELECT application_name, state, sent_lsn, replay_lsn FROM pg_stat_replication;'

# Có job nào đang chạy không
kubectl get jobs -n cozyroom-k8s --field-selector=status.active=1
"
05 · Sau khi bật lại

Checklist sau khi máy khởi động

Verify từng lớp từ dưới lên: WSL2 → K3S → postgres → backend → full API test.

Layer 2 — Postgres

Layer 3 — Backend & API

Layer 4 — Registry & Misc

One-shot verify sau restart

wsl -d Ubuntu-22.04 -- bash -c "
echo '=== Nodes ==='
kubectl get nodes

echo '=== Pods ==='
kubectl get pods -n cozyroom-k8s

echo '=== Postgres standby in recovery? ==='
kubectl exec -n cozyroom-k8s statefulset/postgres-standby -- \
  psql -U cozyroom -c 'SELECT pg_is_in_recovery();' 2>/dev/null || echo 'standby pod not ready yet'

echo '=== Replication lag ==='
kubectl exec -n cozyroom-k8s statefulset/postgres -- \
  psql -U cozyroom -c 'SELECT application_name, state, write_lag, replay_lag FROM pg_stat_replication;' 2>/dev/null || echo 'primary pod not ready yet'

echo '=== Registry ==='
docker ps --filter name=k3s-registry --format 'Registry: {{.Status}}'
"
Nếu standby đã bị promote (pg_is_in_recovery = f): Điều này không nên xảy ra do monitor bị blocked. Nếu xảy ra (do can thiệp tay), phải thực hiện: (1) Stop backend + db-adapter, (2) Stop postgres primary, (3) Dùng promoted standby làm primary mới, (4) Re-setup streaming replication. Liên hệ nếu cần hỗ trợ — đây là thao tác nguy hiểm.

K3S auto-start — ✓ Đã set

  • systemctl is-enabled k3s → enabled
  • systemctl is-active k3s → active
  • Khi Windows reboot → WSL2 khởi động → K3S systemd tự start. Không cần can thiệp tay.

Registry auto-start — ✓ Đã set

  • docker inspect k3s-registry → RestartPolicy=always
  • Container tự restart khi Docker daemon khởi động lại.
  • Pods đang chạy không cần registry để tiếp tục — chỉ cần cho kubectl apply mới
