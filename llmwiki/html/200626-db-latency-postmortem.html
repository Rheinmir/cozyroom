Sao nó mượt lại rồi nhỉ?

HAProxy routing DB connections qua Tailscale IP bị broken — mỗi query timeout 60s → site đứng → down hoàn toàn. Fixed bằng 4 patches không restart DB.

01 · Triệu chứng

Từ "loading lâu" tới "down luôn r"

Ba giai đoạn suy giảm — từ chậm đến đứng đến tắt hoàn toàn trong vài giờ.

🐢
Giai đoạn 1 — Loading lâu

Chữ (artists, albums) tải chậm hơn hồi xưa dùng replica. Spinner hiện nhưng rồi data xuất hiện. Backend logs bình thường.

⏳
Giai đoạn 2 — Kẹt ở đang tải

Spinner mãi không tắt. Network tab thấy request tới /api/artists pending >30s. DB timeout bắt đầu xuất hiện trong logs.

💀
Giai đoạn 3 — Down luôn r

Mọi API call fail. Logs liên tục: dial tcp 10.43.187.77:5432: connect: connection timed out. DB hoàn toàn không accessible từ backend.

02 · Root Cause

HAProxy routing qua Tailscale IP bị broken

db-adapter HAProxy cố kết nối tới 100.88.197.64:5432 (Tailscale IP) — nhưng Tailscale connectivity từ K8s pod tới IP đó bị broken. Postgres chỉ accessible qua K8s service DNS postgres:5432.

Tại sao Tailscale IP bị broken?

  • Postgres chạy trong K8s pod, KHÔNG expose qua hostPort hay NodePort
  • ClusterIP chỉ accessible nội bộ cluster — không qua Tailscale
  • HAProxy pod gọi 100.88.197.64:5432 → Tailscale route nhưng không có service lắng nghe
  • TCP connect timeout sau 60s → cả request chain bị block

Tại sao postgres:5432 hoạt động?

  • K8s Service postgres có ClusterIP nội bộ cluster
  • HAProxy pod cùng namespace cozyroom-k8s → DNS short name postgres resolve được
  • CoreDNS resolve postgres → postgres.cozyroom-k8s.svc.cluster.local
  • Traffic đi trong K8s network, không cần Tailscale

04 · 4 Bản Vá

Fixes được apply trong session

Theo thứ tự ưu tiên — infra fix trước, query optimization sau, tất cả không restart DB.

Fix #1 — Critical

HAProxy route: Tailscale IP → K8s DNS

Root cause chính. Đổi backend server trong HAProxy config từ hardcoded Tailscale IP sang K8s service name.

Trước

server primary
100.88.197.64:5432
(Tailscale — broken)

Sau

server primary
postgres:5432
(K8s DNS ✓)

Fix #2 — Stability

db-adapter node affinity

Tránh pod schedule lên rhein-e2144g (broken networking). Khớp pattern của cloudflared + frontend.

Trước

Không có node affinity → random schedule → CrashLoop trên e2144g

Sau

NotIn: [rhein-e2144g] → chỉ schedule trên node healthy

Fix #3 — Performance

stats: 3 queries → 1 subquery

/api/stats chạy 3 COUNT(*) riêng lẻ = 3 round-trips. Với Tailscale latency ~20ms/round-trip = 60ms chỉ để đếm 3 bảng.

Trước · 3 queries

COUNT(*) FROM artists
COUNT(*) FROM albums
COUNT(*) FROM tracks

Sau · 1 query

SELECT
(SELECT COUNT(*) FROM artists),
(SELECT COUNT(*) FROM albums),
(SELECT COUNT(*) FROM tracks)

Fix #4 — Performance

artistDetail: 3 queries → 1 LEFT JOIN

/api/artists/{id} chạy 3 queries: lấy tên, đếm albums, đếm tracks. Merge thành 1 LEFT JOIN.

Trước · 3 queries

SELECT name FROM artists
SELECT COUNT(*) FROM albums
SELECT COUNT(*) FROM tracks JOIN...

Sau · 1 query

SELECT a.name,
COUNT(DISTINCT al.id),
COUNT(DISTINCT t.id)
FROM artists a
LEFT JOIN albums...
LEFT JOIN tracks...
