T1 · Backend — softstate read cache (Basically Available) Claude main

Hiện tại mỗi GET nóng (artists, albums, tracks, stats, search, trending, playlists) đi thẳng từ handler qua PgBouncer xuống Postgres, nên khi Postgres chết thì toàn bộ API trả 500 và người dùng mới không mở được app. Task này thêm package internal/softstate nằm giữa handler và DB: khi truy vấn thành công, kết quả được giữ lại làm bản sao với TTL fresh 60 giây; khi truy vấn thất bại, thay vì trả lỗi, handler trả bản sao cũ kèm header X-Data-Freshness: stale để client biết mình đang xem dữ liệu tạm. Đây chính là chữ "BA" trong BASE — hệ thống luôn trả lời được, chỉ là không cam kết dữ liệu mới nhất.

Rủi ro chính là vỡ read-your-writes: user tạo playlist xong mà GET playlists trả bản cache cũ thì trải nghiệm như bị mất dữ liệu. Vì vậy mọi write thành công cùng domain phải invalidate key cache tương ứng ngay lập tức. Cache cũng phải cap số entry bằng LRU để RAM backend không phình, và tuyệt đối không cache response stream audio/video.

T2 · Backend — outbox write-behind (Eventually consistent) Claude main

Bốn route ghi "mềm" — POST /api/playback/progress, POST /api/playback/error, POST /api/lastfm/scrobble, POST /api/ebooks/{id}/progress — hiện ghi đồng bộ vào Postgres, nên DB chết là write mất luôn. Task này thêm package internal/outbox: handler chỉ append bản ghi vào file JSONL trên /data/outbox/ (persistent volume đã mount sẵn) rồi trả 202 Accepted ngay; một goroutine flusher chạy nền, mỗi 5 giây gom batch đẩy xuống Postgres, gặp lỗi thì retry với backoff và giữ nguyên hàng đợi. Khi pod khởi động lại, outbox replay các dòng chưa flush — write không mất kể cả khi pod chết giữa chừng.

Ngữ nghĩa là at-least-once, nên phải xử lý ghi trùng: playback progress vốn là upsert nên tự idempotent; riêng lastfm scrobble cần khoá idempotency theo cặp (track, timestamp) để không scrobble đôi khi retry. Các write "cứng" — playlists CRUD, AI memory, NSFW flag, lyrics save — giữ nguyên synchronous vì user cần thấy kết quả ngay sau khi bấm.

T3 · Frontend — freshness indicator (Soft state hiển thị được) Claude main

Service worker hiện đã StaleWhileRevalidate cho catalog nên FE vốn quen sống với dữ liệu cũ, nhưng người dùng không hề biết khi nào mình đang xem bản tạm. Task này cho api.ts đọc header X-Data-Freshness từ T1 và expose một state đơn giản; khi giá trị là stale, một badge nhỏ "⏳ dữ liệu tạm thời cũ" hiện lên và tự ẩn khi backend fresh trở lại. Hợp đồng degradation trở nên tường minh thay vì âm thầm.

Bài học từ sự cố blank page sw.js/Cloudflare (postmortem 180626): task này tuyệt đối không đụng cấu hình precache hay tên service worker sw2.js — chỉ sửa api.ts và thêm một component badge. Nhờ vậy rủi ro regression gần như bằng không.

T4 · Chaos verify — BASE end-to-end trên K3s Claude main + user giám sát

Đây là bài kiểm tra chứng minh cả ba chữ cái của BASE cùng lúc trên cluster thật. Bước một, scale deployment Postgres về 0 (chỉ tắt pod, không đụng PVC hay dữ liệu, tuân thủ rule bảo vệ DB trong CLAUDE.md — bước này chỉ chạy khi user xác nhận). Bước hai, xác nhận app vẫn duyệt được: GET trả 200 kèm header stale, và POST progress trả 202 với dòng mới trong file outbox. Bước ba, scale Postgres lên 1 và đo: toàn bộ hàng đợi phải flush trong tối đa 60 giây, số liệu play count/progress trong DB khớp đúng số request đã gửi lúc DB chết — không mất, không trùng.

Kết quả (log, số liệu đối chiếu, screenshot badge stale) được ghi lại vào wiki làm bằng chứng. Nếu bất kỳ bước nào lệch — ví dụ flush trùng scrobble hay outbox không replay sau restart — đó là bug chặn merge, không phải "chấp nhận được".
