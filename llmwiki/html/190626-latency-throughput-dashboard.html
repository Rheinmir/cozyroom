01 · Tổng quan

Kiến trúc & request path

Mỗi request từ browser đi qua nhiều lớp. Tổng latency = tổng RTT qua từng hop. CF Tunnel là điểm tập trung — nó vừa là ingress vừa là CDN nếu cache được bật.

Request path đầy đủ. SW Cache hit → chỉ browser. CF Edge hit → miss cloudflared/nginx/backend. Miss → đi full stack.
Cache layers hiện tại
  • L1 Service Worker — artists/albums/stats StaleWhileRevalidate
  • L1 Service Worker — images/covers CacheFirst
  • L2 CF Edge — audio lossless public max-age=3600
  • L2 CF Edge — images 7 ngày public max-age=604800
  • L3 Go memory — YT search 5 min in-memory map
  • ❌ tracks API — no cache NetworkFirst 4s
Bottleneck thực sự
  • 🏠 Home upload bandwidth — giới hạn concurrent streams
  • 📡 CF Tunnel RTT — ~20ms Vietnam → Singapore (fixed, hardware)
  • 🐍 yt-dlp cold start — ~3-5s (mitigated by debounce+cache)
  • 🔊 ffmpeg transcode — ~500ms startup cho 320kbps (by design)
  • ✅ Go HTTP, PostgreSQL, Disk I/O — không phải bottleneck ở quy mô hiện tại

03 · Streaming

Audio streaming performance

Streaming latency phụ thuộc vào loại file và cache state. Lossless passthrough hưởng lợi từ CF edge; transcode path không cache được (streaming response, không có Content-Length).

Lossless passthrough: CF cache giảm latency từ 350ms → 20ms lần 2. 320kbps transcode không cache được — by design.
Tại sao lossless cache được?
  • ✓ http.ServeFile → Go tự set Content-Length
  • ✓ Supports HTTP Range (206 Partial) → CF cache Range responses
  • ✓ Cache-Control: public, max-age=3600 → CF nhận
  • ✓ URL = /stream/{hex-id} deterministic → same URL = same bytes
  • ✓ TTL 1h đủ cho session nghe nhạc; file đổi → ID mới → cache miss tự nhiên
Ước tính tiết kiệm bandwidth
  • FLAC avg bitrate: ~1.4 Mbps
  • Nếu 10 người nghe bài phổ biến: 10 × 1.4 = 14 Mbps
  • Sau CF cache: lần 2-10 → CF serve, home bandwidth = 0
  • Savings: 9/10 requests × 1.4 Mbps = 12.6 Mbps tiết kiệm
  • → Effective capacity tăng 10× cho bài phổ biến
