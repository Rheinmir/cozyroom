DB trong K8s Pod là Antipattern

Tại sao HAProxy lại có Tailscale IP? Tại sao master-slave làm phức tạp thêm không lợi? Và kiến trúc DB nào đúng cho homelab một người dùng?

01 · Biên Niên

Kiến trúc DB đã thay đổi 5 lần

Từ SQLite đơn giản đến Citus 3 node rồi lại về Postgres đơn — mỗi bước để lại "di vật" trong config.

📦
SQLite — file duy nhất trong Docker volume 2025–early 2026

Toàn bộ data trong 1 file /m/data/metadata.db. Simple, zero config, zero network latency. Hoạt động tốt cho homelab 1 người dùng. Không có replication, không có HA.

✓ Phù hợp với usecase
🐘
Migrate → Postgres — chạy native trên host May 2026

Nâng cấp lên Postgres để hỗ trợ concurrency tốt hơn, full-text search, JSONB. Postgres chạy ngoài K8s — Docker on host hoặc bare metal. Backend kết nối trực tiếp qua host IP.

✓ Kiến trúc đúng — DB ngoài K8s
🗺️
Plan: db-adapter + 2 Postgres nodes 16/06/2026

Thiết kế HAProxy db-adapter nằm giữa Backend và các Postgres node. Postgres vẫn chạy ngoài K8s — mỗi node vật lý có Postgres riêng tại Tailscale IP. HAProxy config: server primary 100.88.197.64:5432 — node 1 Tailscale IP.

✓ Design đúng — HAProxy biết Tailscale IP vì DB ở ngoài K8s
🌀
Plan: Citus distributed — coordinator bare metal 18/06/2026

Nâng cấp lên Citus với coordinator trên Node-1 100.88.197.64:5432 (Docker on host). db-adapter trỏ vào coordinator qua Tailscale. Plan này explicitly loại bỏ "DB trong K8s pod" (❌3 trong danh sách).

⚠ Quá phức tạp cho homelab — bị abandon
💥
Fallback: postgres:16-alpine vào K8s pod — config không đổi 2026-06-19

Citus bị abandon → deploy Postgres trong K8s StatefulSet. Nhưng HAProxy config không được cập nhật — vẫn trỏ 100.88.197.64:5432 (Tailscale). Postgres trong K8s pod không expose port đó. Đây là mầm mống của outage.

❌ DB vào K8s pod — mâu thuẫn với thiết kế ban đầu
❌ HAProxy config legacy — không ai cập nhật
✅
Fix: HAProxy → postgres:5432 (K8s service DNS) 20/06/2026

Cập nhật db-adapter config để dùng K8s service DNS thay vì Tailscale IP. Đây là fix tình thế — DB vẫn trong K8s pod, không phải kiến trúc lý tưởng.

✓ Site up — nhưng kiến trúc vẫn chưa ideal
02 · Giải Phẫu Config

Tại sao HAProxy lại có Tailscale IP?

Di vật từ thiết kế đúng — khi Citus coordinator chạy bare metal, Tailscale IP là cách đúng để reach nó. Vấn đề là postgres sau đó vào K8s mà config không theo.

Thiết kế ban đầu — HAProxy đúng

  • db-adapter trỏ 100.88.197.64:5432 vì đó là Tailscale IP của node chạy Postgres bare metal
  • Citus coordinator exposed port 5432 trực tiếp trên host — không qua K8s service
  • Tailscale routing giữa K8s pod và bare metal host — hoạt động bình thường
  • Kiến trúc này nhất quán: DB ngoài K8s, HAProxy biết IP trực tiếp

Điều gì gãy — khi DB vào K8s

  • Postgres StatefulSet trong K8s chỉ expose qua ClusterIP service nội bộ
  • Port 5432 của pod KHÔNG bind lên host interface hay Tailscale — không có hostPort
  • HAProxy gọi 100.88.197.64:5432 → Tailscale routing đến host → không có gì lắng nghe
  • TCP timeout sau 60s → mọi DB query bị block
03 · Antipattern

Tại sao DB trong K8s pod là sai

K8s được thiết kế cho stateless workloads. Đưa stateful DB vào K8s pod thêm complexity mà không thêm lợi ích thực sự cho homelab.

"Tôi chưa bao giờ muốn cho DB vào pod K8s để scale. Tệ nhất là mô hình master-slave."

— User, 2026-06-20
💾

Data persistence fragile

hostPath volumes bind data vào 1 node vật lý. Node bị reschedule → data access lỗi. StorageClass, PV, PVC — overhead lớn cho dữ liệu cá nhân.

Nguy hiểm
🔄

Pod restart = cold start

K8s có thể kill pod bất cứ lúc nào (OOMKill, node drain). Postgres khởi động lại → recovery time, WAL replay → downtime không cần thiết.

Unreliable
🌐

Network hop thêm

App → K8s Service → iptables → Pod. Mỗi query thêm 1 network hop. Với DB là high-frequency calls, latency cộng dồn rõ ràng.

Slow
⚙️

StatefulSet phức tạp

StatefulSet, PV, PVC, StorageClass, headless service — chỉ để chạy 1 Postgres instance. Docker on host + volume mount đơn giản hơn 10x.

Overengineered
🔍

Debug khó hơn

Khi DB có vấn đề: phải kubectl exec vào pod, logs phân tán. Bare metal: psql trực tiếp, tail -f /var/log/postgresql/ ngay trên host.

Hard to debug
📏

Scale DB ≠ thêm pod

DB scale bằng read replica, sharding, connection pooling — không phải chạy thêm pod stateless. K8s scaling model không áp dụng cho DB.

04 · Over-engineering

Master-slave: phức tạp hơn lợi ích

Streaming replication giải quyết vấn đề production scale — cho team dev, traffic cao, SLA nghiêm ngặt. Homelab 1 người dùng không có vấn đề đó.

Những gì master-slave thêm vào

  • 2 Postgres instances cần maintain (primary + standby)
  • WAL streaming config (wal_level=replica, max_wal_senders)
  • pg_basebackup init, replication slot, primary_conninfo
  • Failover logic — tự động (Patroni) hoặc thủ công (pg_promote())
  • postgres-monitor CronJob chạy mỗi 2 phút kiểm tra health
  • Telegram alert integration cho promote event
  • db-adapter HAProxy để route giữa primary/standby

Lợi ích thực sự với homelab

  • HA — Khi primary down, standby promote sau ~30s. Nhưng primary down bao giờ? Homelab reboot thì down cả cluster luôn.
  • Read scaling — Route read queries tới standby. Nhưng 1 người dùng không có read scaling problem.
  • Zero downtime backup — Backup từ standby. Nhưng pg_dump từ primary chạy <10s.
  • Tổng kết: Lợi ích tồn tại nhưng không đủ bù đắp complexity đã thêm vào.
05 · Recommendation

Kiến trúc DB đúng cho Cozyroom homelab

Stateful thì không vào K8s. Đơn giản hóa stack DB xuống mức tối thiểu phục vụ được 1–5 người dùng đồng thời.

Kiến trúc mục tiêu

  • Postgres chạy ngoài K8s — Docker on host hoặc systemd service trên node chính
  • Expose qua host interface (hoặc Tailscale IP) — K8s backend kết nối trực tiếp hoặc qua HAProxy với IP thật
  • Nếu dùng HAProxy db-adapter — dùng Tailscale IP của host running Postgres, không phải K8s pod
  • Backup: pg_dump hàng ngày via cron, lưu ra local disk hoặc NAS
  • Không cần replication cho 1–5 người dùng — MTTR <5 phút nếu restore từ dump là chấp nhận được
  • Nếu thực sự cần HA sau này: PostgreSQL native streaming replication ngoài K8s, không trong pod

Bước migrate DB ra khỏi K8s

  • pg_dump cozyroom > cozyroom.sql từ pod hiện tại
  • Chạy Postgres trên host: docker run -d -p 5432:5432 postgres:16
  • psql < cozyroom.sql restore vào host postgres
  • Cập nhật DATABASE_URL trong backend.yaml → host IP hoặc Tailscale IP thật
  • Xóa StatefulSet + PV + PVC trong K8s — dọn sạch

Trade-offs khi không dùng replication

  • MTTR nếu DB die: Restore từ pg_dump gần nhất (~<5 phút nếu backup hourly)
  • Data loss window: Tối đa 1 giờ nếu backup hourly — chấp nhận được với music app
  • Maintenance window: Postgres restart ~5s — không đủ để justify full HA stack
  • Lợi ích bù lại: Không cần HAProxy, không cần monitor CronJob, không cần Telegram alert, stack đơn giản hơn 10x
